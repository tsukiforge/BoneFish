## 4. Turbo Mode Analysis
--------------------------------------------------------------------------------
HISTORICAL TURBO MODE (v5.1.0 - v6.3.1)
Turbo Mode tidak punya FastFlag sendiri; ia alias dari preset Extreme:

    EnableTurboMode = true
      -> OptimizeForLowEnd = true
      -> ForceExtremeMode   = true
      -> ApplyAggressiveOptimizations(SystemTier.ExtremePerformance)
      -> Save() + FastFlags.Save()

    EnableTurboMode = false
      -> OptimizeForLowEnd = false, ForceExtremeMode = false
      -> RemoveOptimizations()

- Preset yang diaktifkan   : ExtremePerformance, seluruhnya.
- Flag yang diterapkan     : set lengkap Extreme (FRM=3, texture=0,
                             LowResFactor=1, FrameBuffer=4, Threads=4, jobs=1,
                             grain=0, animation tracks=32, telemetry off, network).
- Flag yang dihapus saat OFF: semua ManagedFlags via RemoveOptimizations().
- Mengubah FPS cap         : YA secara kode
                             (DFIntTaskSchedulerTargetFps = clamp(
                              ExtremeModeFpsTarget, 24, 60)), TAPI flag itu sudah
                             tidak di allowlist sejak 2025-09-29 => tidak ada cap nyata.
- Mengubah kualitas render : YA, agresif.
- CPU/memori               : DFIntMaxFrameBufferSize=4,
                             FIntRuntimeMaxNumOfThreads=4; branch Ultra/Extreme
                             mematikan EnableFpsMonitor + EnableRobloxNotifications.
- Auto-reset saat restart  : YA (v5.1.0-v6.3.1 Bootstrapper memaksa OFF).

RANTAI PERBANDINGAN

    Historical Turbo Mode
            |
            v
    Current equivalent
      ExperimentalViewModel.EnableTurboMode (baris 469-500) MASIH IDENTIK:
      OptimizeForLowEnd=true + ForceExtremeMode=true +
      ApplyAggressiveOptimizations(ExtremePerformance);
      OFF -> RemoveOptimizations()
            |
            v
    Missing behavior
      Auto-reset saat restart DIHAPUS di v7.x (Bootstrapper "FIX 2"),
      sengaja sebagai preferensi persisten.
            |
            v
    Potential regression
      Bila user pernah menyalakan Turbo Mode, kini ia MENEMPEL PERMANEN dan
      memaksa ForceExtremeMode=true setiap boot. Pada device ini,
      ForceExtremeMode=true + storage Unknown memilih jalur LOD TERBERAT
      500/750 (lihat bagian 7). Bukti terukur di dalam repo: Turbo/Extreme
      ON = 36-40 FPS, OFF = 50-60 FPS. Jadi jalur Turbo/Extreme justru dapat
      MENURUNKAN FPS dibanding tidak mengaktifkan apa pun.

Tidak diimplementasikan apa pun pada tahap ini.

## 5. v5.3.0 Analysis
--------------------------------------------------------------------------------
RAM CLASSIFICATION
  Diperbaiki dari integer division bytes/(1024^3) (8GB terbaca 7GB -> salah ke
  LowEnd) menjadi perbandingan MB dengan toleransi:
      >= 15600 MB -> HighEnd
      >=  7800 MB -> MidRange
      <   3800 MB -> UltraLow
  Nilai ini MASIH IDENTIK di current. Jadi klasifikasi RAM user (MidRange)
  tidak pernah berubah sejak v5.3.0.

STORAGE DETECTION
  DeviceIoControl + IOCTL_STORAGE_QUERY_PROPERTY +
  StorageDeviceSeekPenaltyProperty pada \\.\C:.
  BIAS "GAGAL -> ASUMSI HDD" di 3 tempat:
     1. buka volume gagal
     2. IOCTL gagal
     3. exception
  Inilah akar misklasifikasi HDD<->SSD yang diperbaiki bertahap sampai
  v7.7.0 (3-state).

HDD BALANCED PRESET
  Basis  : ExtremePerformance penuh (FRM=3, texture=0, LowResFactor=1, grain=0,
           LOD 250/250/250/250)
  Plus   : I/O khusus HDD
             FIntRuntimeMaxNumOfThreads        = 4
             DFFlagEnableRequestAsyncCompression = True
             DFIntTextureCompositorActiveJobs  = 2
             DFIntTaskSchedulerTargetFps       = 30      <-- FLAG MATI
             telemetry OFF
  Auto   : HDD + tier LowEnd/MidRange + belum pilih preset manual -> JALAN OTOMATIS.
           Untuk device user (MidRange + HDD), v5.3.0 adalah versi TERAKHIR yang
           otomatis menerapkan set berat ini.

THREAD LIMIT & FPS CAP DI v5.3.0
  Keduanya hanya EFEKTIF SEBAGIAN:
    - FIntRuntimeMaxNumOfThreads  : masih allowlist (efektif)
    - DFIntTaskSchedulerTargetFps : SUDAH MATI (tidak allowlist sejak 2025-09-29)

PENTING (sesuai peringatan prompt)
  "Cap 30" v5.3.0 BUKAN konfigurasi 110 FPS. Konfigurasi itu adalah
  performance optimization untuk I/O HDD. v5.3.0 tetap bukan sumber 110 FPS.

YANG HILANG DI CURRENT
  - Semua tuning HDD otomatis (karena storage Unknown)
  - LOD 250/250 HDD (diganti 500/750 generik)
  - FIntRuntimeMaxNumOfThreads=4 (dibuang v7.2.7)

## 6. v6.0.0 Analysis (Fast Loading)
--------------------------------------------------------------------------------
v6.0.0 Fast Loading (toggle independen):
    DFIntTextureCompositorActiveJobs = 2   bila cpuCores >= 4
    FIntRuntimeMaxNumOfThreads       = 6   bila cpuCores >= 8

Nilai di current 100% IDENTIK (ApplyFastLoadingFlags() baris 1568-1600).

Aspek                          | Temuan
-------------------------------|------------------------------------------------
Kapan diterapkan               | Saat toggle ON; di-re-apply di AKHIR
                               | ApplyAggressiveOptimizations (prioritas HIGHEST)
                               | dan setelah setiap preset UI
Ambang CPU                     | jobs=2 -> >=4 core; threads=6 -> >=8 core
Stack dengan preset?           | Ya, sengaja — tidak pernah jadi preset berdiri sendiri
Current masih apply?           | Ya, prioritas tertinggi; bahkan menimpa nilai jobs preset
Bisa menurunkan FPS?           | BERPOTENSI. jobs=2 menaikkan paralelisme kompositor =
                               | lebih banyak akses disk/CPU bersamaan. Pada i3 2C/4T
                               | + HDD, saat streaming aset ini menambah contention.
                               | FPS cap tidak berubah sama sekali.
Konflik dengan logika optimasi | YA: pada device user FIntRuntimeMaxNumOfThreads
                               | TIDAK PERNAH ditulis (cores 4 < 8), sedangkan
                               | DFIntTextureCompositorActiveJobs dinaikkan 1->2.
                               | Jadi Fast Loading di device ini HANYA menambah
                               | concurrency, tanpa komponen thread.

CATATAN: FIntRuntimeMaxNumOfThreads=4 (patokan "thread dibatasi", alasan HDD head
tidak oleng) secara eksplisit DIBUANG di v7.2.7 dan TIDAK dikembalikan oleh Fast
Loading kecuali cores >= 8.

FLAG YANG SUDAH DITOLAK (tidak di allowlist) saat riset v6.0.0:
    FFlagEnableAsyncResourceLoading
    FIntRenderChunkLODThreshold
    FFlagEnableTextureStreamingFix
    FIntPartSizeBoostThreshold

Tidak mengasumsikan "Fast Loading" = FPS lebih tinggi.

     => YA. refreshRate hanya DI-LOG, tidak dipakai:

        Ini disengaja.

  G  Perubahan prioritas CPU

        log tail), Discord RPC, crosshair overlay (default off),

  J  Optimasi SSD kena HDD
     => TIDAK.

  K  Game Session mengganggu Roblox
     => TIDAK — dan WAJIB DIPERTAHANKAN.

  L  Urutan launch/restart mereset konfigurasi
     => TIDAK mereset, tapi ADA SILENT NO-OP (lihat di bawah).

KANDIDAT REGRESI PALING SIGNIFIKAN (berurut bukti)

1) LOD 500/750 pada Extreme tetap terpasang saat storage Unknown.
   ApplyAggressiveOptimizations:
       isHDD = GetStorageType() == Hdd;         // Unknown => false
       ...L23/L34 = isExtreme && !isHDD ? "500" : "250"
   => 500/750. Mitigasi HDD-aware (v7.0.2) TIDAK PERNAH aktif pada user yang
   storage-nya Unknown.
   Komentar resmi di source menyatakan arahnya:
     "Nilai Extreme 500/750 membuat geometri TETAP high-poly lebih jauh
      (switch LOD semakin jauh) = beban render lebih berat = FPS turun di
      perangkat 'potato' (bukti: LANGKAH 0 user — Extreme ON 36-40 FPS vs
      OFF 50-60)."
   Ini satu-satunya bukti FPS terukur yang ada di repo, dan device-nya kelas
   yang sama dengan user.

2) ForceExtremeMode bisa jadi SILENT NO-OP.
   Bypass guard manual-preset hanya aktif bila:
       ForceExtremeMode && GetStorageType()==Hdd &&
       trueTier in {LowEnd, MidRange}
   Karena storage Unknown, hddCombo=false => bypassLowEndGuard=false =>
   jika user pernah menekan preset manual (mis. "Balanced"),
   ApplyAggressiveOptimizations RETURN LEBIH AWAL dan Extreme tidak menulis
   apa pun. Toggle menyala, efek nol, tanpa warning di UI.

3) Set penurun beban render v5.x/v6.x HILANG SELURUHNYA
   (FRM=3, texture=0, LowResFactor=1, FrameBuffer=4, Threads=4, grain=0,
    light updates, telemetry, animation tracks).
   Ini DISENGAJA untuk white-screen, tetapi konsekuensinya current secara
   harfiah LEBIH BERAT untuk dirender dibanding v5.x/v6.x pada hardware yang
   sama. Ini kandidat utama untuk persepsi "sekarang lebih lambat".

4) Batas thread hilang. FIntRuntimeMaxNumOfThreads=4 tidak lagi pernah ditulis
   pada CPU 2C/4T (Fast Loading butuh >=8 core). Scheduler Roblox kini tak
   dibatasi pada CPU kecil. Belum ada bukti arah dampaknya => UNKNOWN, bukan
   alasan untuk mengembalikan flag.

5) Fast Loading di device ini hanya menaikkan concurrency jobs 1->2 tanpa
   komponen thread; di HDD ini menambah beban seek saat streaming.

6) FramerateCap lifecycle (item B/C): penulisan 240 tanpa memperhitungkan
   refresh rate, dan penghapusan elemen saat OFF.

7) Overhead permanen v7.x (tray/log tail/Discord/overlay) — kecil, tapi tidak
   ada di v5.x, dan tidak pernah diukur.

## 10. Safe Fixes
--------------------------------------------------------------------------------
Diurutkan; SEMUANYA BELUM DIIMPLEMENTASIKAN.

1) [bukti kuat] LOD tidak boleh menurunkan FPS saat storage tidak diketahui.
   Ubah keputusan LOD agar jalur berat 500/750 hanya dipakai bila storage
   DIKONFIRMASI bukan-HDD, atau lebih konservatif: UNKNOWN diperlakukan seperti
   HDD untuk LOD (turun ke 250/250).
   Tidak menebak jenis storage, tidak menyentuh logika deteksi, dan memakai
   nilai yang sudah ada di kode.
   Ini fix terkecil dengan dasar bukti paling jelas.

2) [safe, keputusan user] Hilangkan silent no-op ForceExtremeMode.
   Bypass guard manual-preset jangan bergantung pada
   GetStorageType()==Hdd; cukup pada INTENT EKSPLISIT user menyalakan
   ForceExtremeMode, atau minimal LOG PERINGATAN + tampilkan status di UI saat
   guard memblokir. Tidak mengubah nilai flag.

3) [perlu benchmark] Fast Loading: jangan naikkan TextureCompositorActiveJobs
   ke 2 saat storage Unknown/HDD tanpa bukti.
   Ini eksperimen, bukan kepastian — jalankan skenario C/D dulu.

4) [hardening, bukan FPS] FramerateCap lifecycle:
   - gunakan GetPrimaryDisplayRefreshRate() sebagai sanity check
     (sekarang hanya di-log)
   - JANGAN hapus elemen saat toggle OFF jika nilainya bukan milik BoneFish;
     pulihkan nilai sebelumnya
   - jangan timpa cap manual user secara diam-diam

5) [diagnostik] Perluas panel System Info yang sudah ada (sudah read-only) dengan:
     versi BoneFish
     preset aktif
     FPS cap efektif DAN nilai sebelumnya
     graphics level Roblox
     storage type + model
     tier asli / efektif
     status Fast Loading / TDR / Game Session
     daftar FastFlag aktif
     priority proses
   Read-only dulu.

6) [JANGAN] Eksplisit jangan mengembalikan FIntRuntimeMaxNumOfThreads=4,
   DFIntDebugFRMQualityLevelOverride, texture override, atau flag deprecated
   lain. Bila benchmark menunjukkan thrash, solusinya harus mekanisme allowlisted
   yang BARU DIVERIFIKASI, bukan flag lama.

7) [JANGAN DISENTUH] Game Session + daftar proteksi (Windows/security/audio/
   Realtek/mic/Voice Chat, elevated, verifikasi suspend), Discord RPC, crosshair,
   dan logika kepercayaan storage detection.

## 12. Final Recommendation
--------------------------------------------------------------------------------
BUKTI YANG ADA
- Nama FastFlag nyaris tidak berubah antara v5.0.0 dan current; yang berubah
  adalah NILAI, PATH EKSEKUSI, dan flag mana yang berhenti ditulis.
- Kap FPS di v5.x-v6.x memakai DFIntTaskSchedulerTargetFps, yang SEJAK
  2025-09-29 TIDAK ADA DI ALLOWLIST — artinya versi lama TIDAK PERNAH benar-benar
  membatasi FPS lewat BoneFish, sedangkan current justru SECARA AKTIF mengelola
  FramerateCap. Jadi "110 FPS dulu, sekarang tidak" lebih mungkin dijelaskan oleh
  cap yang dulu kebetulan tidak pernah aktif / diatur Roblox sendiri, bukan oleh
  penghapusan optimasi. INI BELUM TERBUKTI TANPA BENCHMARK.
- Yang JELAS dan bisa diuji adalah satu perbedaan beban render: jalur Extreme
  menulis LOD 500/750, dan mitigasi HDD-aware-nya MATI saat storage Unknown
  (kondisi device user). Repo ini sendiri mencatat arah dampaknya
  (Extreme ON 36-40 FPS vs OFF 50-60).
- Sejak v7.2.7 seluruh set penurun beban render v5.x/v6.x DIBUANG karena
  menyebabkan white-screen pada Intel iGPU + driver 2020 — hardware user.
  Ini pertukaran stabilitas<->FPS yang disengaja, bukan kelalaian.

JALUR TEKNIS PALING AMAN (urut; berhenti untuk evaluasi di tiap langkah)
  1. Jalankan protokol benchmark bagian 9 skenario A-D dulu.
     Tanpa itu, tidak ada dasar untuk mengubah flag apa pun.
  2. Bersamaan dengan itu, terapkan HANYA fix #1 (LOD Unknown -> 250/250) karena
     dasar buktinya sudah ada di dalam repo dan perubahannya tidak menebak
     storage, tidak mengembalikan flag deprecated, tidak menyentuh Game Session/
     Discord/crosshair.
  3. Perbaiki silent no-op ForceExtremeMode (fix #2) agar status di UI jujur —
     tanpa mengubah nilai flag.
  4. Jalankan ulang benchmark. Bila C/D tidak berbeda dari B, BERHENTI — berarti
     masalahnya bukan di FastFlag, melainkan di driver iGPU/TDR, HDD streaming,
     atau ekspektasi cap. Jangan mengejar FPS dengan mengembalikan flag lama.
  5. Pertimbangkan fix #3/#4 hanya jika benchmark menunjukkan efek; lalu
     dokumentasikan di CHANGELOG.md beserta angka mentahnya.

TIDAK BOLEH DILAKUKAN
  - mengembalikan DFIntTaskSchedulerTargetFps, DFIntDebugFRMQualityLevelOverride,
    texture override, DFIntMaxFrameBufferSize, atau flag non-allowlist lain
  - menurunkan kepercayaan deteksi storage demi memicu tuning HDD
  - mengorbankan proteksi Game Session
  - mengklaim kenaikan FPS tanpa hasil benchmark

STATUS: Tidak ada kode yang diubah pada tahap ini. Implementasi menunggu keputusan
        atas fix #1 dan hasil benchmark bagian 9.
